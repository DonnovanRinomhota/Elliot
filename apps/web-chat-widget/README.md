# Elliot Web Chat Widget

The embeddable chat bubble a client puts on **their own** website, for
**their** customers to talk to Elliot through. Not the marketing site --
that's the separate [`Elliot-web`](https://github.com/DonnovanRinomhota/Elliot-web)
repo, kept separate on purpose (see `ROADMAP.md` in the main repo for why).

## Why this isn't a Next.js app

Earlier versions of this README described a "Next.js chat widget." That
doesn't actually work for what this needs to do: a widget embedded on a
third-party site can't require React/Next.js to be running on *their*
page. Real chat-widget products (Intercom, Crisp, Drift, etc.) all ship a
single, dependency-free JS file loaded via `<script src="...">`, rendering
into a Shadow DOM so its styles can never collide with the host site's
CSS. That's what `widget.js` is.

## Usage

A client adds one line to their own site:

```html
<script
  src="https://elliot-real-estate-five.vercel.app/widget.js"
  data-tenant="their-tenant-slug"
  async
></script>
```

Optional attributes on the same tag:

| Attribute | Default | Purpose |
|---|---|---|
| `data-title` | `"Chat with us"` | Header text |
| `data-greeting` | `"Hi! How can I help you today?"` | First bubble shown before the visitor sends anything. **This is static UI text, not generated by Elliot** -- the chat webhook requires a real message to respond to, so there's no way to get a real AI-authored opening line before the visitor has said something. |
| `data-accent` | `#111111` | Accent color (hex) |
| `data-webhook-url` | production chat webhook | Override for local testing against a different n8n instance |

## How it talks to the backend

Directly to the `chat` webhook (`01-main-ai-agent.json`), no intermediary:

```
POST { tenant_slug, message, conversation_id? }
  -> { conversation_id, reply }
```

`conversation_id` is stored in `sessionStorage` (keyed per tenant) once the
first reply comes back, and sent on every message after that so the
conversation threads correctly. Deliberate tradeoff: `sessionStorage`
means a conversation survives page navigation within the same tab/session
but resets on a new tab or browser restart -- swap to `localStorage` in
`widget.js` if longer persistence across visits matters more than that.

## Local testing

Open `demo.html` directly in a browser -- no build step, no server. It
loads `widget.js` from the same folder with a test tenant slug. Point
`data-webhook-url` at a real n8n instance to test against live data.

Automated tests (jsdom, mocked `fetch`) cover mounting, sending, error
handling, XSS-safety of rendered replies, and conversation-id persistence.
Run from a scratch Node project with `jsdom` installed:

```js
// see the test file used to verify this widget for the exact assertions;
// not checked into this repo since it's a one-off verification harness,
// not part of the shipped product -- write a fresh one if this file changes.
```

## Known gaps, not yet resolved

- **CORS not verified live.** The `chat` webhook's n8n node has no explicit
  CORS configuration (`options: {}`), so this relies on n8n's default
  cross-origin behavior. **Test this for real** by embedding the script on
  an actual third-party domain (not `localhost`) before handing this to a
  client -- if the browser console shows a CORS error, the fix is in the
  webhook node's Options (add an explicit `Allowed Origins` value), not in
  this file.
- **No auth on the webhook**, same as every other n8n webhook in this
  project so far (see the main repo's `KNOWN_ISSUES.md`). Anyone who finds
  the URL and a real `tenant_slug` can call it directly.
- **Deployment is a manual copy, not automated.** `widget.js` needs to be
  copied to `apps/elliot-dashboard/public/widget.js` to actually be served
  (see the main repo's deploy notes) -- there's no build step wiring this
  up automatically yet, so it's easy for the two to drift out of sync if
  one gets edited and not the other.
